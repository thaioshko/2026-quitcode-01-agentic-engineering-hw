## 2. Де агент спіткнувся і як ми його розвернули

Найбільша заминка — **Porsche Design System не рендерилась стилізовано**. Послідовність діагностики:

1. Перевірили, що скрипт з CDN (`cdn.ui.porsche.com`) справді завантажився і кастомні елементи (`p-button`, `p-input-text` тощо) зареєстровані (`customElements.get(...)` → `yes`).
2. Через `shadowRoot.adoptedStyleSheets` знайшли, що стилі компонентів **посилаються** на CSS-змінні токенів (`var(--p-color-primary)` тощо), але самі токени ніде на сторінці не визначені — ні в `document.adoptedStyleSheets`, ні в жодному `<style>`.
3. Висунули гіпотезу, що причина — нестандартний User-Agent автоматизованого браузер-пейну (`Claude/1.44...`), який ніби блокує ін'єкцію токенів у клієнтському завантажувачі Porsche.
4. Користувач попросив звірити з офіційним сайтом `designsystem.porsche.com` (сторінка Button Tile) — той сайт відрендерився повністю стилізовано в тому ж браузер-пейні. Це спростувало гіпотезу «браузер взагалі не може» — офіційний сайт просто використовує інший механізм (Next.js SSR + partials), а не клієнтський CDN-лоадер, який ми підключили.
5. Розвертальний промпт користувача: *«ок, як мені переглянути все що ти зробив?»* → далі, коли стало зрозуміло, що повноцінний фікс (SSR partials) вийде за межі 15-хвилинного Task 1 — новий продуктовий запит («design is pretty shitty, I need a prompt for claude design... sunset colors») по суті став сигналом переключитись на власну дизайн-систему замість Porsche.
6. Фінальний промпт, який зняв блокер: **«adapt is to the home task» / «make it to be acceptable to home task requirements»** — після чого замінили Porsche DS на Tailwind + CSS-токени, і все запрацювало з першого разу.

## 4. Спостереження — що зробили б інакше наступного разу

1. **Перевіряти готову дизайн-систему в реальному, а не лише в автоматизованому браузері, одразу** — якби ми з першої хвилини звірили Porsche DS у справжньому Chrome, а не в sandbox-пейні, ми б швидше зрозуміли, що проблема специфічна для середовища, а не для коду, і одразу перейшли б до альтернативи (custom DS), не витрачаючи час на глибоку діагностику client-loader'а.
2. **Не довіряти автоматизованому кліку миші наосліп** — коли UI-взаємодія «не спрацьовує», варто одразу перевірити через пряме `element.click()`/DOM-інспекцію, перш ніж підозрювати код застосунку. Це зекономило б один зайвий раунд перевірки.
3. **Розділяти сесії за задачею** — 44% зваженої вартості пішло на «reasoning без інструментів», що частково є наслідком однієї дуже довгої сесії з кількома непов'язаними гілками роботи (домашка + окремий дизайн-мокап). Наступного разу вартість Task 1–4 було б чистіше виміряти в окремій, сфокусованій сесії.
